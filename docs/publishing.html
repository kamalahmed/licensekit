Publishing LicenseKit

A complete walkthrough from "I have working code" to "live on wordpress.org/plugins/licensekit". Written for first-time submitters; assumes no SVN experience.

Timeline at a glance

PhaseWhat you doHow long
1. GitHubPush code, tag v0.1.0, GitHub Actions builds the zip.~30 min
2. WP.org accountCreate your wordpress.org account.~5 min
3. Build clean zipStrip dev files, run Plugin Check.~15 min
4. SubmitUpload to plugins.svn.wordpress.org submit form.~10 min
5. WaitReviewers respond by email.1–6 weeks
6. SVN basicsCheck out, commit, tag.~30 min one-off
7. Go liveListing publishes within minutes of your first commit.~15 min
8. UpdatesBump version → tag in SVN.~10 min each
9. Automate(Optional) GitHub Action deploys to SVN on tag.~30 min one-off
Plan for ~6 weeks total. The wp.org review queue is the bottleneck and entirely outside your control. The active work on your end is roughly 2 hours, spread across the timeline above.

Phase 1: GitHub

Account & repo

  1. Sign in to github.com.
  2. Click + → New repository.
  3. Name it licensekit. Public. Do not add a README, .gitignore, or LICENSE — we already have ours.
  4. Create.

First push

cd "/Users/kamalahmed/Local Sites/wp/app/public/wp-content/plugins/licensekit"

# Sanity: only commit what should be public.
git status

# Initialize and push
git init -b main
git add .
git commit -m "Initial release v0.1.0"
git remote add origin git@github.com:kamalahmed/licensekit.git
git push -u origin main

Open the repo on GitHub. The Actions tab should show Tests and PHPCS running on your push. Both should turn green within ~3 minutes.

Tag the release

git tag v0.1.0
git push origin v0.1.0

This triggers the release.yml workflow which builds licensekit-0.1.0.zip and attaches it to the Releases page on GitHub. Anyone can install from that zip immediately.

You're done with GitHub. Existing customers can clone or download the zip from your Releases page. Now move on to WP.org for wider distribution.

Phase 2: WP.org account

  1. Visit login.wordpress.org/register.
  2. Pick a username. This is permanent and public — it'll show up as the plugin author on every install. Use the same handle you used in readme.txt's Contributors: line. We have kamalahmed there.
  3. Confirm your email.

The wp.org username and the slug you'll claim later (licensekit) are different things — usernames identify you, slugs identify the plugin.

Phase 3: Build a clean submission zip

Reviewers want a zip that looks exactly like what you'd ship to a customer — no dev tooling, no tests, no vendor/ folder unless required.

cd "/Users/kamalahmed/Local Sites/wp/app/public/wp-content/plugins/licensekit"

# Install production dependencies (no dev deps).
composer install --no-dev --optimize-autoloader

# Stage a clean copy.
mkdir -p /tmp/lk-submit/licensekit
rsync -a \
  --exclude='/.github' \
  --exclude='/.git' \
  --exclude='/.gitignore' \
  --exclude='/.phpunit.cache' \
  --exclude='/build' \
  --exclude='/coverage' \
  --exclude='/tests' \
  --exclude='/docs' \
  --exclude='/phpunit.xml.dist' \
  --exclude='/phpcs.xml.dist' \
  --exclude='/CONTRIBUTING.md' \
  --exclude='/SECURITY.md' \
  --exclude='/CHANGELOG.md' \
  --exclude='/_debug*' \
  ./ /tmp/lk-submit/licensekit/

# Make the zip.
cd /tmp/lk-submit
zip -rq licensekit-0.1.0.zip licensekit
ls -lh licensekit-0.1.0.zip

# Restore dev dependencies in your working copy.
cd "/Users/kamalahmed/Local Sites/wp/app/public/wp-content/plugins/licensekit"
composer install

Then run one final pass through Plugin Check on your local WordPress against the zipped version:

  1. WP admin → Plugins → Add New → Upload Plugin → upload licensekit-0.1.0.zip.
  2. Activate it under a different folder if needed (or temporarily deactivate the dev copy).
  3. Tools → Plugin Check → select LicenseKit → Run Checks.
  4. You should see 0 errors. Warnings are tolerated; errors block submission.

Phase 4: Submit for review

  1. Sign in at wordpress.org/plugins/developers/add/.
  2. Read the rules. They're short, take 5 minutes — every word matters.
  3. Upload licensekit-0.1.0.zip.
  4. Submit.

You'll see a confirmation page with your tracking number. The slug licensekit is now reserved in your name — even before approval, no one else can claim it.

Phase 5: The review process

Reviewers will respond by email. Common outcomes:

OutcomeWhat it means
ApprovedYou'll receive SVN credentials and instructions. Skip to Phase 6.
Approved with commentsMinor issues to fix in your next commit. Approval still happens.
Needs changesSpecific issues that must be fixed before approval. Reply to the email with a new zip.
RejectedRare; usually because of guideline violations (trademark, incompatible license, etc.). Reviewers explain why.
Reply to all reviewer emails promptly. Submissions that go silent for 30+ days get closed and you have to start over. If you need more time, just say so.

Typical wait time: 1–6 weeks. Sometimes faster, sometimes slower. Don't email them asking for status — your message goes to the bottom of the queue.

Phase 6: SVN crash course

SVN vs Git in 2 minutes

You only need to know three things to publish a WordPress plugin via SVN:

ConceptGit equivalentWhat it does
svn checkout URLgit cloneDownload the entire SVN repo to your laptop.
svn add + svn commitgit add + git commit + git pushStage and upload changes to the server in one step (no local commits).
svn copy for tagsgit tag + pushMark a version. SVN tags are real directory copies, not metadata pointers.

You don't need branching, merging, or rebasing for plugin distribution. WordPress only cares about trunk/ (the always-current dev version), tags/ (released versions), and assets/ (banners and icons).

The repo layout

https://plugins.svn.wordpress.org/licensekit/
├── trunk/                    ← your latest code (mirrors a working copy)
│   ├── licensekit.php
│   ├── readme.txt
│   ├── src/
│   ├── client-sdk/
│   └── ... etc
├── tags/                     ← real directory copies of trunk at each release
│   ├── 0.1.0/
│   ├── 0.1.1/
│   └── 0.2.0/
└── assets/                   ← banners, icons, screenshots (NOT shipped to users)
    ├── icon-128x128.png
    ├── icon-256x256.png
    ├── banner-772x250.png
    ├── banner-1544x500.png  (high-DPI)
    ├── screenshot-1.png
    └── screenshot-2.png
The Stable tag: line in your readme.txt is what controls which version users actually download. If Stable tag: 0.1.0, then tags/0.1.0/ is what gets installed — even if trunk/ has newer code. To roll back, edit Stable tag in trunk/readme.txt back to a known-good version.

Check out your repo

First, install SVN if it's not already on your Mac:

brew install svn

Then check out your wp.org repo to a directory of your choice:

cd ~
mkdir wp-svn && cd wp-svn

# This URL comes from your approval email; the path /licensekit/ is your slug.
svn checkout https://plugins.svn.wordpress.org/licensekit/ licensekit-svn
cd licensekit-svn

# After checkout you'll see three empty directories:
ls
# assets/  branches/  tags/  trunk/

branches/ exists by convention but plugins don't use it. Ignore it.

First commit to trunk

Your trunk should mirror exactly what's in your release zip. Easiest path: copy the staged release files into trunk.

# From the SVN checkout root:
cd ~/wp-svn/licensekit-svn

# Copy the prepared release files into trunk.
rsync -av --delete /tmp/lk-submit/licensekit/ trunk/

# Tell SVN about new files.
svn status                    # Lists files with ?, !, or M markers
svn add trunk/* --force       # Stage everything new

# Commit. The first commit may be large — be patient.
svn commit -m "Initial v0.1.0 release"

SVN will prompt for your wp.org password. After commit, your plugin's listing page goes live within ~15 minutes.

Tag your release

SVN tags are directory copies. To release v0.1.0 officially:

svn copy trunk tags/0.1.0
svn commit -m "Tagging v0.1.0"

Now tags/0.1.0/ exists as a permanent snapshot. Confirm readme.txt's Stable tag: 0.1.0 matches.

Upload banner + icon

The assets/ folder lives outside trunk and isn't shipped to users — these images only appear on your wp.org listing page.

FileSizePurpose
icon-128x128.png128 × 128Standard icon (Plugins screen, search results)
icon-256x256.png256 × 256Retina icon
banner-772x250.png772 × 250Top of your listing page
banner-1544x500.png1544 × 500Retina banner
screenshot-1.pngup to 2880 × 1800First screenshot — referenced as "1" in readme.txt's Screenshots section
screenshot-2.pngSecond screenshot, etc.
 
# Drop your image files into ./assets/ then:
svn add assets/*
svn commit -m "Add banner, icon, screenshots"
If you don't have artwork yet, ship without it. The plugin still works perfectly. You can add banner + icon any time later with another svn commit. A placeholder gradient is better than waiting.

Phase 7: Going live

~15 minutes after your first svn commit:

  • Your listing page goes live at https://wordpress.org/plugins/licensekit/.
  • The plugin appears in WordPress admin's Plugins → Add New search.
  • Anyone can install it from their WP admin without ever visiting your site.
  • If you tagged 0.1.0, that's what they install.
Smoke test from a fresh WP: spin up a clean WordPress install and search "LicenseKit" in Plugins → Add New. Install. Activate. Verify it works end-to-end. If anything's broken on a fresh install that worked locally, fix it in trunk and bump the patch version (see Phase 8).

Phase 8: Subsequent updates

For every new release:

  1. In your dev repo (Git side):
    • Make changes. Commit and push to GitHub.
    • Bump the version number in three places: licensekit.php header, readme.txt Stable tag:, and licensekit.php's LICENSEKIT_VERSION constant.
    • Add a = 0.1.1 = section to readme.txt's Changelog.
    • Tag in Git: git tag v0.1.1 && git push origin v0.1.1. GitHub Actions builds the zip and attaches it to the Releases page.
  2. In your SVN checkout: 
    cd ~/wp-svn/licensekit-svn

# Pull any other tags or external changes (rare for solo dev).
svn update

# Sync trunk from the new release files.
rsync -av --delete /tmp/lk-submit/licensekit/ trunk/

# Track new files / removals.
svn status
svn add trunk/* --force
svn commit -m "Release v0.1.1"

# Tag the new release.
svn copy trunk tags/0.1.1
svn commit -m "Tagging v0.1.1"
  3. Within ~15 minutes, every site with auto-updates enabled sees the new version.

Phase 9: Automating SVN from GitHub

Manual SVN gets tedious. The standard fix is the 10up/action-wordpress-plugin-deploy action — it watches for Git tags, pushes the matching release to SVN trunk and tags automatically.

Add this workflow file to your repo:

# .github/workflows/wp-org-deploy.yml
name: Deploy to WordPress.org

on:
  push:
    tags:
      - "v*.*.*"

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Setup PHP
        uses: shivammathur/setup-php@v2
        with:
          php-version: "8.1"
          tools: composer:v2

      - name: Install production dependencies
        run: composer install --no-dev --optimize-autoloader

      - name: Deploy to WordPress.org
        uses: 10up/action-wordpress-plugin-deploy@stable
        env:
          SVN_USERNAME: ${{ secrets.WP_SVN_USERNAME }}
          SVN_PASSWORD: ${{ secrets.WP_SVN_PASSWORD }}
          SLUG: licensekit

Then in your GitHub repo: Settings → Secrets and variables → Actions → New repository secret:

NameValue
WP_SVN_USERNAMEYour wp.org username (e.g. kamalahmed)
WP_SVN_PASSWORDYour wp.org password (or app password)

From now on, your release flow is just:

git tag v0.1.1
git push origin v0.1.1
# … 5 minutes later, v0.1.1 is live on wp.org.
This action handles the same things you'd do manually: reads .distignore or .gitattributes to exclude dev files, syncs to trunk, copies trunk to tags/<version>, and uploads anything in .wordpress-org/ to assets/.

If something goes wrong

SymptomLikely cause / fix
Plugin Check shows errors after uploadRun Tools → Plugin Check on your local WP first. Fix every error. PCP errors are blocking.
"Slug already exists" on submissionSearch wp.org for the slug. If a closed/abandoned plugin holds it, you'd need to email plugins@wordpress.org with a takeover request.
Reviewer asks for changesReply to their email. Attach a fresh zip. Expect a few rounds.
svn commit fails with auth errorDouble-check your wp.org username/password. The first commit specifically may need --username your_username.
Pushed wrong code to trunksvn revert + redo the rsync. Or commit a fix forward — SVN doesn't punish bad commits.
Customers report "license invalid" after I rotated wp-config secretsYou broke the signing keypair on your shop site. Customers' SDKs verify with the old public key. Either revert the secret or ship a plugin update with the new public_key.
Want to roll back a bad releaseEdit readme.txt in trunk: change Stable tag: to a known-good version. Commit. New installs revert immediately. Then push a fix forward.

This guide describes WP.org's process as of 2026. If anything reads outdated, please open an issue.
